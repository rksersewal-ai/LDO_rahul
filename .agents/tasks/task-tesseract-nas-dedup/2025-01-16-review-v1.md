# Tesseract OCR, NAS storage, and background dedup scan

Three features land together: real OCR via Tesseract.js replaces the degraded image-processing stubs, a NAS-backed storage service replaces local `readFile`/`toFile` in the OCR worker, and the dedup scan is moved from a synchronous tRPC mutation to a BullMQ background job with admin-facing settings UI and scan history. The changes total ~1,800 lines across 14 files and introduce one new runtime dependency (`tesseract.js`).

Watch for:
- **O(n²) pair comparison in the dedup worker** with no upper-bound guard — a workspace with 10,000 documents creates ~50 million pair evaluations in a single job (confirmed).
- **Tesseract fed a raw PDF buffer** for image-only PDFs — Tesseract expects raster image input, not PDF byte streams (confirmed).
- **`getScanHistory` leaks cross-workspace data** — the query has no workspace filter (confirmed).
- **Upsert race in `updateScanSettings`** — insert-then-update pattern is not atomic and can double-insert under concurrent requests (likely).

---

## High-level view

The Tesseract integration wraps `tesseract.js` with a timeout and never-throw contract, but the image-only PDF path feeds the raw PDF buffer directly to Tesseract rather than first rendering pages to images — Tesseract cannot parse PDF and will silently produce garbage or empty output for those documents.

The NAS storage service introduces content-addressed file paths, workspace isolation, and retry-with-backoff. The retry helper retries all errors uniformly, which means `fileExists` on a genuinely absent file incurs ~7 seconds of backoff before returning `false`.

The dedup scan is now a BullMQ job with a `dedup_scan_history` table tracking each run's lifecycle. The worker implements both "basic" (hash+docNumber+metadata) and "advanced" (full scorer with OCR trigrams and PL overlap) modes. The O(n²) nested loop with no document-count cap is the primary scalability concern. The scan history query returns all workspaces' data to any admin, which is an information-leak if the system is multi-tenant.

The admin UI adds scan settings management backed by the settings table, a "Run Now" panel, and a scan history table. Settings are persisted via an insert-then-update pattern that creates a subtle race condition under concurrent saves.

1. **PDF-to-Tesseract format mismatch** — `recognizeImage` receives the raw PDF buffer for image-only PDFs, but Tesseract.js cannot parse PDF byte streams. Render PDF pages to PNG (e.g., via `pdf-poppler` or `sharp`) before passing to Tesseract.

3. **`getScanHistory` returns all workspaces** — add a `where(eq(dedupScanHistory.workspaceId, workspaceId))` clause so admins only see their own workspace's scans.
4. **Upsert race in `updateScanSettings`** — the insert-then-update sequence is not wrapped in a transaction. Use Drizzle's `onConflictDoUpdate` or a serialized transaction.
5. **No worker lifecycle management** — `createDedupWorker()` and `createOcrWorker()` are exported but no code calls them or handles graceful shutdown. Without a runner entry point, the workers never start.
6. **NAS retry retries `fileExists` on genuine absence** — `fileExists` wraps a `stat` call in `withRetry`, meaning a legitimately missing file incurs 3 retries with exponential backoff (~7 s) before returning `false`.
7. **Tesseract worker created per image** — each call to `recognizeImage` spins up and tears down a Tesseract WASM worker. For batch OCR on multi-page documents this is expensive; consider pooling or reusing workers across calls.

## Tesseract OCR integration and the PDF gap

In `ocr-worker.ts`, when a PDF has fewer than 100 characters of extracted text (line ~60), the code hands `fileBuffer` — which is the raw PDF byte stream — directly to `recognizeImage`. Tesseract.js accepts image buffers (PNG, JPEG, TIFF, BMP, WebP) but does not contain a PDF parser. The call will either produce empty text (Tesseract's WASM engine fails to decode the bytes) or garbage characters if the PDF's binary content happens to map to recognizable pixel patterns. The never-throw contract means this failure is silent — the worker will record `confidence: 0.3` and move on, making it look like a low-confidence scan rather than a format error.

To fix: render each PDF page to a raster image before calling Tesseract. Libraries like `pdf-to-img` or direct use of `sharp` (which can rasterize PDFs on some builds) would close this gap.

Each invocation of `recognizeImage` also creates a WASM worker, loads the English trained data, performs recognition, and terminates. For a multi-page PDF where the fix would iterate pages, the overhead of N worker creations becomes significant. A pooled or reused worker would reduce latency.

## NAS storage retry semantics

`fileExists` calls `stat` inside `withRetry`. If the file genuinely doesn't exist, `stat` throws `ENOENT` on every attempt, so `fileExists` takes ~7 seconds to return `false` (1s + 2s + 4s delays). The fix: catch `ENOENT` specifically inside the retry loop and return `false` immediately, only retrying on transient I/O errors (`EIO`, `EAGAIN`, `ETIMEDOUT`).

## O(n²) dedup scan and the missing upper bound

The dedup worker fetches all non-deleted documents in a workspace and compares every unique pair in a nested loop. For `n` documents, that's `n*(n-1)/2` comparisons. With `batchSize = 500`, the cancellation check fires every 500 iterations of the *outer* loop, not every 500 pairs — so cancellation granularity is coarse (up to 500 × n inner iterations between checks).

```
for i in 0..n:
    if i % batchSize == 0: check cancellation
    for j in i+1..n:
        score pair (i, j)
```

With 5,000 documents the scan produces ~12.5M pair evaluations. At even 0.1ms per pair (optimistic for the advanced scorer which computes trigram sets), that's ~20 minutes of CPU-bound work on a single thread. The worker runs with `concurrency: 1`, so no other dedup job can execute during this time. The UI's batch-size input controls the insert flush interval, not the document count — there's no cap on how many documents enter the comparison loop.

A blocking/bucketing strategy (group by hash, then by document number, then score only within buckets) would reduce complexity from O(n²) to near-linear for typical workloads.

## Cross-workspace data leak in `getScanHistory`

The `getScanHistory` endpoint (line 340 of `dedup.ts`) queries `dedupScanHistory` with no workspace filter:

```ts
getScanHistory: adminProcedure.query(async () => {
  const history = await db.select().from(dedupScanHistory)
    .orderBy(desc(dedupScanHistory.startedAt)).limit(20);
  return history;
});
```

An admin in workspace A can see scan history (including error messages, timing, and detection counts) from workspace B. Other endpoints (`getPendingDuplicates`, `triggerScan`) do filter by workspace — this one was missed.

## Settings upsert: insert-then-update without a transaction

`updateScanSettings` iterates each key, inserts with `onConflictDoNothing`, then unconditionally updates the same row in a second query:

```ts
await db.insert(settings).values({ ... }).onConflictDoNothing();
// then immediately:
await db.update(settings).set({ value, ... }).where(eq(settings.key, update.key));
```

Two concurrent calls can both succeed at `onConflictDoNothing` if the row doesn't exist yet — one insert wins, the other is a no-op, and then both issue updates. The last update wins silently. Additionally, the `where` clause matches on `(scope = 'system' AND key = ...)` but not on `scopeId` — if other scopes ever use the same key names, the update could hit the wrong row.

The idiomatic fix is `onConflictDoUpdate` with the unique constraint target.

## Worker lifecycle: exported but never started

Both `createOcrWorker()` and `createDedupWorker()` return `Worker` instances, but nothing in the codebase calls these factory functions. There's no runner script, no server-side initialization hook, and no graceful-shutdown handler. The `triggerScan` mutation will successfully enqueue jobs that sit unprocessed until a worker process is started externally.

## Test coverage gaps

The dedup worker tests validate `scoreDocumentPairBasic` scoring logic thoroughly but only verify that `processDedupJob` and `createDedupWorker` are exported — no integration test of actual job-processing logic (database interactions, batch flushing, cancellation). The admin UI has no component or E2E tests.

Not tested: the PDF-to-Tesseract path in `ocr-worker.ts` (which would reveal the format mismatch), NAS retry behavior under transient errors (tests only verify the final failure message), concurrent settings updates, or the `getScanHistory` workspace leak.

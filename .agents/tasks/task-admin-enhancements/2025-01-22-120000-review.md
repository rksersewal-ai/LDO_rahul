# Admin control center, user security management, work notifications, and hierarchical KPI reports

Four features shipped together: a tabbed admin settings page with feature toggles, security policies, role permission matrix, compliance settings, and import/export; admin-controlled password reset and account lock/unlock with security badges in the user table; work assignment notifications with a "My Pending Works" tab; and a reports page rewrite with user filtering, individual/comparative views, and CSV export.

The approach is entirely client-side state with mock data — no real database, no real authentication enforcement at the UI layer beyond role-gating the user filter dropdown. The tRPC endpoints exist but are never called by the page components (pages read from mock data directly).

**Watch for:** plaintext password storage in resetPassword endpoint (confirmed), importSettings lacks schema validation and allows arbitrary JSON to overwrite configuration state (confirmed), and `getUserProductivity` endpoint exposes all users' data to any authenticated user without role check (confirmed).

## High-level view

The admin settings page is a 1,800-line page component with seven tabs. State lives in `useState` hooks at the page level, so all settings reset on navigation. The tRPC admin router mirrors this with endpoints for every settings domain, but the UI never calls them — it operates on local mock data clones.

User security management adds password reset and account lock/unlock to both the admin tRPC router and the users page via two new dialog components. The admin router stores reset passwords in plaintext on the in-memory user object. The UI-side handlers refresh dialog state after mutations using a read-before-write pattern on stale closures.

Work notifications adds an `assignWork` endpoint behind `supervisorProcedure` and a `getMyPendingWorks` endpoint behind `protectedProcedure`. The notifications page gains a second tab that directly filters `MOCK_WORK_RECORDS` client-side with a hardcoded user ID (`"user-001"`) rather than the session user.

The KPI reports page gains a filter bar and three view modes. The `getUserProductivity` endpoint uses `protectedProcedure`, meaning any logged-in user can query productivity stats for all users — the role check described in the task spec was not implemented server-side.

<summary>Issues (7)</summary>

1. **Plaintext password in resetPassword** — The admin router stores `input.newPassword` directly on the user object without hashing. Add bcrypt or equivalent before persisting, even for mock data, to establish the correct pattern.
2. **importSettings accepts arbitrary JSON** — `JSON.parse(input.data)` with no zod schema means any shape overwrites feature toggles, security policies, and system config. Validate the imported payload against the same schemas used by the individual update endpoints.
3. **getUserProductivity exposes all users without role check** — Uses `protectedProcedure` (any authenticated user), but returns productivity data for every user. Should be gated to `supervisorProcedure` or filter results to the caller's own data for non-admin/supervisor roles.
4. **lockAccount hardcodes admin ID** — `users[idx].lockedBy = "u-001-admin"` instead of using `ctx.session.user.id`. Loses audit trail if another admin exists.
5. **Stale-closure risk in security dialog handlers** — `handleLockAccount` calls `users.find()` on the pre-setState array to refresh `securityUser`. After `setUsers()`, `users` still references the old array. The dialog may show stale data until re-render.

7. **Roles Overview card shows static "13/13 perms"** — The overview tab renders a hardcoded string for every role instead of computing actual permission counts from `rolePerms` state.

<summary>Details</summary>

## Plaintext password handling in admin router

The `resetPassword` mutation stores the new password directly:

```typescript
users[idx].password = input.newPassword;
```

The `MockUser` interface has a `password` field that is already plaintext (`"password123"`), and the reset flow extends this without hashing. If authentication logic reads from this array for credentials (which NextAuth credentials providers commonly do), passwords are compared in clear text. The password reset dialog generates random passwords client-side using `Math.random()` — not cryptographically secure if these values ever leave the browser.

## importSettings: no schema validation on incoming JSON

The import endpoint does `JSON.parse(input.data)` and then spreads whatever comes back over the in-memory stores:

```typescript
securityPolicies = { ...securityPolicies, ...parsed.securityPolicies };
systemConfiguration = { ...systemConfiguration, ...parsed.systemConfiguration };
```

A malformed export file can inject any shape into these stores. The endpoint returns `{ success: false }` on parse failure but has no validation on the parsed structure. The same zod schemas used in `updateSecurityPolicies` and `updateSystemConfiguration` should gate the import path.

## getUserProductivity authorization gap

The task spec says "if caller is not admin/supervisor, only allow querying own userId." The implementation uses `protectedProcedure` with no additional role filtering:

```typescript
getUserProductivity: protectedProcedure
  .input(z.object({ dateFrom: z.string().optional(), dateTo: z.string().optional() }).optional())
  .query(({ input }) => { ... })
```

Any authenticated user can call this and get back productivity stats for every user. The `ctx` parameter isn't even destructured. The client-side reports page gates the UI (`isAdminOrSupervisor`), but the endpoint itself is unprotected.

## Client-side duplication of server logic

Both the reports page and the work router independently compute per-user productivity stats from the same `MOCK_WORK_RECORDS` array using near-identical loops. The page never calls the tRPC endpoint; it re-implements the logic in a `useMemo`. Same pattern in the notifications page: `getMyPendingWorks` exists in the router but the UI directly filters `MOCK_WORK_RECORDS`.

When a real backend arrives, the UI must be rewired from local computation to tRPC calls — a migration that will likely introduce subtle behavioral differences (sorting tie-breaks, date boundary filtering).

## lockAccount hardcodes the acting admin

```typescript
users[idx].lockedBy = "u-001-admin";
```

The mutation receives `ctx` (which carries `ctx.session.user.id`) but ignores it. The `assignWork` mutation in the work router correctly uses `ctx.session.user.id` — the inconsistency suggests an oversight.

## Stale closure in user security handlers

In the users page, `handleLockAccount` does:

```typescript
setUsers(users.map(...));
const updated = users.find((u) => u.id === userId);
if (updated) { setSecurityUser({...updated, lockedAt: ...}); }
```

After `setUsers()`, the `users` variable still references the previous array (React setState is asynchronous). The `find()` returns the pre-mutation user. The dialog state is then manually patched with the fields that should have changed — this happens to produce correct results today, but a single missed field in the manual spread will show stale data. Using the functional form of setState (`setUsers(prev => ...)`) and deriving dialog state from the result would be more robust.

## Hardcoded user identity in notifications

The notifications page defines `const CURRENT_USER_ID = "user-001"` and filters pending works against it. Every user sees the same pending works regardless of who is logged in. The `useSession` hook is available (used in the reports page) but not imported here.

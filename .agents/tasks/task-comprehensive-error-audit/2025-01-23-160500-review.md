# Comprehensive error audit: config, auth, schema, OCR, and formatting

This change sweeps across five areas: dependency/config corrections (Next.js and lucide-react version pins, tsconfig target, drizzle DB name, trpc-provider base URL), an auth lockout auto-unlock after 30 minutes with a bulk-archive status guard, a database schema migration from integer-encoded booleans to native booleans plus fileSize bigint and workspace indexes, OCR worker hardening (filePath validation, stalled-job detection, job-retention caps, reduced default concurrency), and a Biome safe-format pass touching ~105 files. Build, 105 tests, and `tsc --noEmit` all pass.

**Watch for:** No SQL migration accompanies the schema-level type changes (isDeleted boolean, fileSize bigint, plNumber uniqueness constraint change) — deploying this code against an existing database will fail unless a migration is generated and applied first (confirmed). The `document-share-links` schema still uses `integer` for boolean-like columns (`isRevoked`, `allowDownload`), creating an inconsistency with the boolean convention established elsewhere in this diff (confirmed). The auth lockout auto-unlock resets state *before* password verification, meaning a DB-write failure during unlock leaves the account in a half-reset state (likely).

## High-level view

The dependency pins move from exact versions to semver ranges (`next: ^15.3.4`, `lucide-react: ^0.474.0`) and bump the tsconfig target to ES2020. The trpc-provider base URL now respects `NEXT_PUBLIC_APP_URL` instead of hardcoding localhost, and the dead `query-provider.tsx` is removed.

The auth lockout now expires after 30 minutes. The implementation resets the account mid-authorize-flow before checking the password, which means a valid login proceeds in one pass but also means the reset DB write happens even for an attacker entering a wrong password — if that write fails, the account is left in an inconsistent state.

The schema moves `isDeleted` from integer (0/1) to native boolean across documents and document-comments, and changes `fileSize` from integer to bigint. A composite workspace+plNumber unique constraint replaces the global plNumber unique. New composite indexes (workspace+deleted, workspace+status) are added. None of these schema changes are backed by a Drizzle migration SQL file, meaning deployment requires manual migration generation before applying.

The OCR worker validates `filePath` before entering the processing pipeline, adds `stalledInterval: 30000` for BullMQ stalled-job detection, caps job retention at 1000 completed / 5000 failed, and drops the default concurrency from 2 to 1.

Roughly 80% of the diff by line count is Biome reformatting (import ordering, line breaks, trailing commas). No behavioral impact.

1. **Missing SQL migration for schema changes** — The Drizzle schema files change column types (integer to boolean, integer to bigint) and alter constraints (plNumber uniqueness), but no migration SQL was generated in `drizzle/`. BullMQ considers this a successful job (no error thrown). The job will be removed by `removeOnComplete` despite being a failure, and queue-level monitoring will undercount failures. ## Schema migration gap

The Drizzle schema files (`documents.ts`, `document-comments.ts`, `pl-numbers.ts`) change column types and constraints at the ORM definition level, but the `drizzle/` directory has no new migration. The existing migrations stop at `0008_performance_indexes.sql`. The `drizzle/meta/_journal.json` was not modified, confirming no migration was generated.

`eq(documents.isDeleted, false)` will emit `is_deleted = false` in SQL. Against a Postgres table where `is_deleted` is still defined as `integer`, Postgres handles implicit bool/int comparison for 0/1, so the application *might* work. However, the `bigint` change for `fileSize` will cause a column-type mismatch if the DDL isn't updated, and the unique constraint removal on `plNumber` requires an `ALTER TABLE ... DROP CONSTRAINT` that won't happen without a migration.

## Auth lockout auto-unlock timing

```typescript
if (user.lockedAt) {
  const lockElapsed = Date.now() - new Date(user.lockedAt).getTime();
  if (lockElapsed < LOCKOUT_DURATION_MS) {
    return null; // still locked
  }
  // Reset immediately — before password check
  await db.update(users).set({
    lockedAt: null, lockReason: null, failedLoginAttempts: 0,
  }).where(eq(users.id, user.id));
}
// ... then verify password
```

The unlock happens unconditionally once the 30-minute window passes, regardless of whether the current attempt will succeed. If the DB write to reset fails (network blip), the account is left in a state where `lockedAt` is still set but the code has already passed the lock check — subsequent logic proceeds to password verification against a still-locked record. The test suite covers the happy path (expired lock → successful auth) but not the DB-failure scenario.

## Boolean inconsistency in document-share-links

The `resolveShareToken` procedure still compares `link.isRevoked === 1`, which works because the column remains integer. Every other soft-delete/boolean flag in the codebase now uses native `boolean`. A future developer pattern-matching on the codebase will assume boolean and introduce a bug here. This is a maintainability time-bomb rather than a runtime bug today.

## OCR worker filePath validation behavior

```typescript
if (!filePath) {
  await db.update(ocrJobs).set({ status: "failed", errorMessage: "..." })...;
  await db.update(documents).set({ ocrStatus: "failed" })...;
  return; // BullMQ sees this as a completed job
}
```

Returning without throwing means BullMQ marks the job as "completed." The `removeOnComplete: { count: 1000 }` setting will eventually purge this job's record. The database records are correct (ocrJobs status = "failed"), so the application-level audit trail is intact, but queue-level monitoring tools (BullMQ dashboard, Prometheus exporters) will undercount failures. Throwing after the DB updates would give both correct DB state and correct queue-level failure accounting.
